# Задача: разработать FlowLab на .NET 10

Разработай веб-приложение FlowLab — визуальную лабораторию для моделирования производительности и отказоустойчивости backend-систем.

Пользователь задаёт поток запросов, собирает схему из сервисов и очередей, запускает воспроизводимую симуляцию и анализирует задержки, пропускную способность, загрузку узлов и ошибки. Затем он может изменить параметры или включить стратегии устойчивости и сравнить результат с исходным сценарием.

Приложение должно быть пригодно для демонстрации в портфолио .NET-разработчика: чистая архитектура, явные границы модулей, воспроизводимые расчёты, тесты, интерактивная визуализация и понятный README.

## 1. Сначала изучи существующий проект

Перед изменениями:

1. Проверь структуру репозитория, README, существующие проекты, конфигурацию и тесты.
2. Проверь установленный .NET SDK и наличие Docker.
3. Проверь, запущен ли PostgreSQL локально на `localhost:5432`, и доступна ли база с логином `postgres` и паролем `postgres`.
4. Если в репозитории уже есть рабочие решения, сохраняй их, если они не конфликтуют с требованиями ниже.
5. Не заменяй и не удаляй существующие файлы или данные без необходимости.
6. Составь короткий план реализации, затем выполняй работу до состояния, когда приложение можно запустить и проверить.

## 2. Технологии и архитектура

Используй:

- .NET 10;
- ASP.NET Core;
- Blazor Web App с интерактивным серверным рендерингом для интерфейса;
- PostgreSQL и Entity Framework Core для хранения сценариев и результатов;
- SignalR для отправки прогресса симуляции в браузер;
- встроенный `BackgroundService` для выполнения длительных симуляций.

Для первой версии реализуй модульный монолит. Не создавай отдельные микросервисы, брокеры сообщений и дополнительные инфраструктурные компоненты без необходимости.

Раздели код на проекты или ясно отделённые модули по ответственности:

- `FlowLab.Domain` — сущности, правила предметной области, настройки и модели симуляции;
- `FlowLab.Application` — сценарии использования, интерфейсы, команды и запросы;
- `FlowLab.Infrastructure` — PostgreSQL, EF Core, миграции и реализации хранилищ;
- `FlowLab.Web` — Blazor, HTTP API, SignalR и запуск приложения;
- `FlowLab.Simulation` — чистый движок симуляции без зависимости от ASP.NET Core и базы данных;
- проекты тестов для домена, симуляции и важных сценариев приложения.

Если существующая структура проекта предлагает разумный способ выполнить эти требования без лишнего разделения, адаптируй структуру, но сохрани перечисленные границы ответственности.

Не добавляй MediatR, AutoMapper, Redis, Kafka, Kubernetes и другие библиотеки или сервисы только ради количества технологий. Внешние зависимости используй, когда они дают конкретную пользу.

## 3. Движок симуляции

Движок должен быть детерминированным: одинаковые настройки и одинаковый random seed должны приводить к одинаковым результатам.

Используй дискретно-событийную симуляцию. События должны обрабатываться в порядке времени события. Для событий с одинаковым временем используй последовательный номер события как дополнительный критерий сортировки.

Поддержи следующие типы узлов:

- источник запросов;
- сервисный узел;
- очередь;
- внешний сервис;
- приёмник, завершающий маршрут запроса.

В первой версии можно ограничить топологию простой схемой, созданной из этих узлов. Проверяй допустимость конфигурации до запуска симуляции и объясняй пользователю ошибки настройки.

У источника должны настраиваться:

- частота поступления запросов;
- длительность симуляции;
- random seed.

У сервисного узла должны настраиваться:

- количество параллельных обработчиков;
- среднее время обработки;
- вариативность времени обработки;
- вероятность ошибки;
- при необходимости — лимит очереди.

У внешнего сервиса должны настраиваться задержка ответа, вероятность ошибки и периоды повышенной задержки или отказа.

Минимально поддержи модели поступления и обработки:

- постоянный интервал между событиями;
- пуассоновский поток с экспоненциальным интервалом;
- фиксированное или экспоненциальное время обработки.

Используй генератор случайных чисел с явно задаваемым seed. Все случайные значения симуляции должны проходить через него.

### Политики отказоустойчивости

Поддержи конфигурируемые:

- таймаут запроса;
- повторы запроса с экспоненциальной задержкой;
- максимальное число попыток;
- верхний предел задержки между повторами;
- circuit breaker с настраиваемым порогом ошибок и временем открытия.

Повторы не должны создавать бесконечный цикл. Для всех запросов должна быть верхняя граница числа попыток и времени выполнения.

Если реализация политики требует решений, которые нельзя однозначно определить из этого ТЗ, выбери простое и последовательное поведение, задокументируй его и покрой тестом.

### Результаты симуляции

Рассчитывай как минимум:

- общее количество поступивших запросов;
- число успешных и неуспешных запросов;
- процент ошибок;
- пропускную способность;
- p50, p95 и p99 сквозной задержки;
- среднюю и максимальную длину очереди;
- количество запросов, отброшенных из-за заполнения очереди;
- количество повторных попыток;
- загрузку каждого сервисного узла;
- причину завершения каждого неуспешного запроса, если её можно определить.

Определи единицы измерения и используй их последовательно во всём приложении. Например, время симуляции и задержки храни в миллисекундах, а отображаемое время форматируй с подходящей точностью.

Для расчёта процентов и перцентилей обработай случаи, когда выборка пуста или содержит один элемент.

Добавь проверку аналитического частного случая для одной очереди M/M/1. Не используй приближённую формулу как замену симуляции и не представляй результаты учебной модели как точный прогноз реальной системы. Явно опиши допущения симуляции в интерфейсе и README.

## 4. Хранение данных

Сохраняй в PostgreSQL:

- сценарии и их настройки;
- результаты запусков;
- параметры запуска, включая random seed;
- статус и краткую ошибку неудачного запуска, если запуск завершился с ошибкой.

Для сохранённого запуска должно быть возможно определить, на каких настройках он был выполнен.

Используй EF Core migrations. При запуске приложения должна быть понятная инструкция для создания схемы базы. Не скрывай ошибки миграции и подключения к БД за успешным запуском приложения.

Предусмотри удаление сценария и связанных с ним результатов через корректный механизм каскадного удаления или явную операцию удаления.

## 5. Пользовательский интерфейс

Создай аккуратный русскоязычный интерфейс. Он должен нормально отображаться на стандартном экране ноутбука и не требовать специальных разрешений браузера.

Основной экран должен содержать:

1. Список сценариев и кнопку создания сценария.
2. Редактор параметров выбранного сценария.
3. Визуальную схему узлов и соединений.
4. Кнопки запуска, остановки и сброса.
5. Индикатор состояния: создан, ожидает запуска, выполняется, завершён или ошибка.
6. Область метрик и графиков.
7. Возможность сравнить результаты двух запусков одного сценария.

Для первой версии схема может быть предопределённой с редактируемыми параметрами узлов. Если реализуешь редактор связей, добавь проверку корректности графа и понятные сообщения об ошибках. Не трать основное время на сложный drag-and-drop, если это отодвигает работающую симуляцию.

Во время запуска показывай обновление прогресса и основных метрик через SignalR. Не отправляй сообщение для каждого внутреннего события симуляции. Обновляй интерфейс с разумной частотой и не создавай чрезмерную нагрузку.

На графиках покажи как минимум:

- задержку запросов во времени;
- длину очереди;
- загрузку сервисных узлов.

Для сравнения двух запусков отобрази их ключевые показатели рядом и вычисли абсолютное и процентное изменение. Корректно обрабатывай нулевое значение в знаменателе.

Покажи понятные сообщения при ошибке подключения, неверной конфигурации, неудачном запуске и отсутствии сохранённых результатов. Не оставляй ошибки только в серверном логе.

## 6. Жизненный цикл запуска

Реализуй запуск симуляции как отдельную задачу с идентификатором и статусом.

Требования:

- HTTP-запрос на запуск не должен блокироваться до окончания долгой симуляции;
- статус и прогресс можно получать через SignalR и/или HTTP;
- состояние запуска должно сохраняться в понятном виде;
- обработай остановку приложения во время симуляции;
- поддержи отмену запуска по запросу пользователя, если это можно сделать без нарушения согласованности данных;
- при исключении запиши ошибку запуска и не оставляй его навсегда в статусе «выполняется».

При нескольких одновременных запусках избегай неограниченного роста фоновых задач. Добавь простое ограничение параллелизма и понятную реакцию на превышение лимита.

## 7. API и эксплуатация

Добавь минимальный API для ключевых операций:

- получить список и детали сценариев;
- создать, изменить и удалить сценарий;
- запустить симуляцию;
- получить статус и результат запуска;
- сравнить два запуска.

Используй DTO на границе API. Не возвращай напрямую EF-сущности и внутренние объекты движка.

Добавь:

- проверку готовности приложения и подключения к PostgreSQL;
- структурированные логи;
- централизованную обработку ошибок;
- валидацию входных параметров;
- корректные HTTP-статусы и сообщения ошибок.

Не записывай пароль базы данных в логи.

## 8. Docker и подключение к PostgreSQL

У приложения должен быть простой способ локального запуска и Docker-сценарий.

Поскольку единственная обязательная инфраструктурная зависимость — PostgreSQL, поддержи оба варианта подключения:

### Локальная разработка

Сначала проверь доступность PostgreSQL на `localhost:5432` с логином `postgres` и паролем `postgres`.

Если он доступен, приложение должно запускаться локально командой `dotnet run`, подключаясь к нему через конфигурацию Development. Настройка подключения должна задаваться через переменные окружения или `appsettings.Development.json`, но не через секреты, закоммиченные в репозиторий.

Для локального PostgreSQL используй имя базы, например `flowlab`. Опиши в README, как создать базу и применить миграции. Не пытайся менять пароль пользователя или настройки уже работающего PostgreSQL.

### Запуск через Docker

Добавь `Dockerfile` и `docker-compose.yml`, чтобы проект можно было поднять одной командой. Docker Compose должен включать приложение и PostgreSQL, чтобы этот режим работал независимо от установленного на компьютере PostgreSQL.

Пример ожидаемого запуска:

    docker compose up --build

Добавь health check для PostgreSQL и настрой запуск приложения так, чтобы оно ожидало готовности базы. Не публикуй PostgreSQL наружу без необходимости. Если порт опубликован для локального доступа, документируй его и не используй конфликтующий порт.

Поддержи настройку строки подключения через переменные окружения. Не полагайся на `localhost` внутри контейнера: приложение должно обращаться к сервису PostgreSQL по имени сервиса в Compose.

Не создавай лишние контейнеры: для MVP достаточно контейнера приложения и контейнера PostgreSQL. Blazor, API, SignalR и фоновый обработчик могут работать в одном контейнере приложения.

Не делай пароль `postgres` допустимым значением для production. Если Compose использует такие значения только для локальной разработки, явно укажи это в README.

## 9. Тестирование

Добавь содержательные автоматические тесты для важных правил, а не только тесты, повторяющие структуру кода.

Покрой как минимум:

- воспроизводимость симуляции с одинаковым seed;
- различие результатов при изменении seed в сценарии со случайностью;
- порядок обработки событий с одинаковым временем;
- соблюдение количества параллельных обработчиков;
- ограничение вместимости очереди;
- корректность учёта ошибок и успешных запросов;
- таймаут и предел повторных попыток;
- переходы circuit breaker между состояниями;
- расчёт перцентилей;
- сравнение результатов, включая деление на ноль;
- проверку аналитического частного случая M/M/1.

Не пиши тесты, требующие запущенного локального PostgreSQL, для проверки чистой логики симуляции. Для интеграционных тестов используй понятный и воспроизводимый способ запуска базы, например отдельный Docker Compose профиль или Testcontainers, только если это не усложняет обычный запуск.

Запусти тесты и сборку. Исправь найденные ошибки.

## 11. Критерии приёмки

Работа завершена, когда:

1. Приложение собирается на .NET 10.
2. Тесты проходят.
3. Приложение запускается локально с PostgreSQL на `localhost:5432` и учётными данными `postgres` / `postgres`, если такая база доступна.
4. Приложение запускается через `docker compose up --build` с контейнерами приложения и PostgreSQL.
5. Пользователь может создать сценарий, запустить воспроизводимую симуляцию и увидеть результаты.
6. Пользователь может сравнить два запуска с разными настройками.
7. Основные метрики и графики работают, ошибки настройки отображаются понятно.
8. README позволяет другому разработчику запустить проект без дополнительных объяснений.
9. Пароли и другие секреты не закоммичены и не попадают в логи.

В конце работы сообщи:
- какие проекты и основные модули созданы или изменены;
- как запустить приложение локально;
- как запустить его через Docker;
- результаты сборки и тестов;
- известные ограничения или незавершённые пункты.

Не утверждай, что критерий выполнен, если не проверил его командой или ручной проверкой.
