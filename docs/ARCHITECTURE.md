# Архитектурные решения

## Границы зависимостей

| Проект | Ответственность | Зависимости |
| --- | --- | --- |
| Domain | Конфигурация и правила модели | BCL |
| Application | ScenarioService, RunService, DTO, сравнение, порты хранения/очереди | Domain |
| Simulation | Календарь, состояние запуска, сервисные станции, breaker, метрики | Domain |
| Infrastructure | EF Core, PostgreSQL, сериализация и repository implementation | Application |
| Web | Composition root, HTTP endpoints, hosted workers, SignalR, health, errors | Infrastructure, Simulation |
| frontend | React components, hooks, HTTP client, charts | API contracts |

Модульный монолит выбран для одного развёртывания и минимального числа эксплуатационных зависимостей. У Simulation нет ссылок на web/persistence. Application не знает о Channel, SignalR и EF. Папки разделены по ответственности; в домене и Application сохранены короткие namespace проекта, а внутреннее состояние движка закрыто `internal`.

## Запуск — отдельный ресурс

HTTP возвращает 202 и id после сохранения запуска. `RunService` сначала резервирует место через `IRunScheduler`, затем создаёт запись с полным снимком. Ошибка записи освобождает резервирование. Два consumer-а `BackgroundService` читают bounded Channel. Суммарная ёмкость — десять задач, включая выполняющиеся.

У каждого запуска отдельные seeded Random, EventCalendar, ResultAccumulator и станции. Движок не использует DateTime, Task.Delay или реальное время. CancellationToken проверяется между событиями. `Stopwatch` используется только транспортным слоем для ограничения частоты отправки прогресса.

Worker соединяет токены пользователя и приложения. Вычисление и публикация прогресса общаются через отдельный bounded Channel ёмкостью один, политика DropOldest. Это ограничивает буфер при медленном клиенте. Нет `async void`, fire-and-forget вычислений или `GetAwaiter().GetResult()`.

Терминальное состояние сохраняется перед уведомлением браузера. Ошибка сохранения при недоступной БД логируется, consumer остаётся работоспособным. При следующем старте recovery закрывает оставшиеся Queued/Running. При штатной остановке активные запросы отменяются, оставшиеся задачи финализируются recovery. Очередь намеренно не распределённая; второй экземпляр приложения запускать на той же БД нельзя.

## Хранение

Scenario содержит редактируемые метаданные и JSONB настроек. Run имеет собственный JSONB snapshot, JSONB результата, seed внутри снимка, timestamps, status, progress и краткую ошибку. Изменение Scenario не переписывает Run.

Журнал каждой неуспешной операции хранится в отдельном JSONB столбце Run. Он сохраняется атомарно с результатом и исключён из SQL-проекции обычных запросов и истории. Отдельный endpoint выполняет постраничное извлечение на стороне PostgreSQL. Полный журнал не передаётся в UI автоматически.

Внешний ключ Run → Scenario использует ON DELETE CASCADE. Создание запуска и удаление сценария берут row lock на Scenario внутри транзакции: нельзя удалить сценарий между проверкой активных задач и сохранением нового запуска. Удаление при активном запуске возвращает 409.

Чтение использует AsNoTracking, история ограничена последними 100 запусками, есть индекс `(ScenarioId, CreatedAt)`. Миграции проверяются на старте; ошибок подключения не скрывает in-memory fallback. InitialCreate включена в репозиторий.

## Детерминизм и ресурсы

EventCalendar — SortedSet с составным приоритетом `(double time, long sequence)`. Последовательность задаёт устойчивый порядок одинаковых timestamps. Вставка, извлечение и отмена события — O(log E). Завершённая попытка удаляет свой будущий timeout из календаря, поэтому устаревшие таймеры не накапливаются до конца большого запуска. FIFO/LIFO используют LinkedList с сохранёнными дескрипторами: удаление записи очереди и получение её длины — O(1). Запрос хранит записи всех ожидающих ветвей; при завершении попытки они удаляются вместе.

Маршрут компилируется в последовательность этапов. `ParallelWithPrevious` добавляет сервис к предыдущему этапу; иначе создаётся новый этап. Каждый этап запускает все свои сервисы одновременно, а счётчик успешных завершений открывает следующий этап ровно один раз. Очереди и пулы обработчиков общие для всех запросов. `QueuedRequest` хранит версию попытки и продолжение: результат старой попытки после таймаута не продвигает маршрут. Уже начатые вызовы дорабатываются, влияя на загрузку и breaker. Ошибка ветви завершает всю попытку, повтор проходит весь маршрут. У старых JSON-сценариев новые поля имеют значения по умолчанию: последовательный этап и FIFO. Данные хранятся в существующем JSON, миграция схемы БД не требуется.

Версия попытки отделяет устаревшие timeout/completion events. Начатая операция освобождает worker даже после клиентского таймаута, но не завершает запрос повторно. Circuit breaker использует поколения, чтобы старые операции не закрывали новую HalfOpen пробу.

В памяти хранятся сквозные задержки для точных перцентилей и ограниченное число точек графика. Поэтому количество запросов ограничено. Запросы, время и состояния не сериализуются по одному событию и не отправляются в браузер.

## React

`ScenarioSettings.Connections != null` включает граф без циклов. `GraphRuntime` хранит для каждой попытки число неразрешённых предшественников и факт активации узла. После завершения предшественника разрешаются все его связи: выбранные активируются, остальные помечаются пропущенными. Узел запускается один раз после разрешения всех входов, если хотя бы один активен. Поэтому объединение альтернативных ветвей не зависает. Завершение всего задания ждёт все активные ветви. Состояния попыток защищены существующим `Version`.

`Broker` — отдельная станция с общей очередью ожидающих сообщений. Диспетчер выбирает свободного консьюмера по кругу, резервирует слот и активирует ровно одну исходящую связь. Остальные ветви этого сообщения пропускаются. Пул брокера равен сумме обработчиков его консьюмеров. Освобождение слота происходит при завершении фактической обработки консьюмера, даже если попытка уже истекла. Доработка очереди планируется отдельным событием на текущий timestamp, что предотвращает рекурсивное опустошение при открытом breaker. У консьюмера должен быть единственный вход от брокера. Это модель конечного задания с общей политикой повторов, без реальной AMQP-доставки и отдельного publisher response.

`useLab` управляет сценариями и пользовательскими операциями. `useRunStream` отдельно обслуживает SignalR, reconnect, восстановление через HTTP и актуальный progress. Поллинг не создаёт параллельные незавершённые HTTP-запросы.

Editor, topology, results, history и layout — отдельные компоненты. Общие поля и форматирование переиспользуются. Графическая библиотека загружается через dynamic import; основной bundle не ждёт загрузки графиков. Сервер остаётся источником истины для валидации и результатов.

## Что намеренно не добавлено

Нет MediatR, AutoMapper, Redis, Kafka, Kubernetes, отдельного брокера или отдельных сервисов. Нет generic repository поверх EF и искусственных абстракций над каждым классом. Дополнительные технологии не нужны для перечисленных сценариев использования.
